## Source mapping and execution boundaries

Canonical **TC-CS47-01–07** retain the IDs from [Jira's supplemental test table](https://spmg8.atlassian.net/browse/CS-47?focusedCommentId=10135). Cases **08–09** cover additional criteria from the current story description; they do not replace or renumber the original cases.

Jira classifies **01, 02 and 04–07** as Integration and **03** as E2E. The Test Steps / Test Data column preserves those levels and specifies the integration procedure above the retained E2E placeholder. Supplemental **08** is persisted read-model integration and **09** is browser E2E. These supplemental level assignments follow the story's testing sections rather than adding cases to Jira's original numbered table.

The 14 October primary-venue requirement supersedes the earlier all-venues/no-primary attendee-display expectation in **02**. The Organiser still sees all effective venues. The agreed attendance policy uses an explicit Coordinator-set Event registration limit supported by room/session headcounts; primary location is display metadata.

Case **03** checks truthful registration-navigation availability for the delivered phase. Cases **06** and **08** may first verify persisted read projections, but those results must be labelled as read-model evidence. Real replacement and cancellation workflows remain integration obligations under CS-92 and CS-48/54/55 respectively; fixture checks do not prove those workflows. Case **07** requires the live readiness → confirmation → attendee-view path.

No execution result, automation file, completion claim or historical ID remapping is introduced by this specification. Record actual results, dates and tested revisions separately when the E2E placeholders are implemented and run.
