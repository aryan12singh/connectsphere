## Source mapping and execution boundaries

The case IDs and AC references above follow the spreadsheet's CS-48 rows 54–64. **The spreadsheet labels AC10 as proposed, not an accepted Jira criterion.** Its proposed rule is: on a valid `EventConfirmed` with a stable message ID, Event ID, Event version, and attendee-safe Event details, attendance-service creates or updates one local Event record keyed by Event ID; duplicate or older deliveries do not duplicate or roll back the record; message processing creates no registration and preserves any existing registrations. Jira could not be independently read during this alignment.

The spreadsheet's acceptance-criteria cells remain unchanged; case execution records are updated separately. Release 1 excludes waitlisting: a full Event rejects a new registration and creates neither a waitlist row nor waitlist action. The Event limit is the Coordinator-set registration limit; it is not derived from planned attendance or venue capacity. When a Coordinator lowers the limit below existing registrations, all registrations remain, remaining places show zero, and further registration is refused. Database-backed E2E cases use `frontend/e2e`; `frontend/tests` is excluded. The outbox relay retries at 2, 4, 8, 16, 32, then 60 seconds (capped) and polls every 500 ms; Attendance emits an alertable log warning when 100 pending actions accumulate or the oldest pending action reaches 60 seconds.
