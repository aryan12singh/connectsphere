# Event request implementation decisions — 6 October 2026

These decisions describe this branch. They do not change the team's Definition of Done or imply customer acceptance. Sources: current CS-11/27/29/44 Jira cards, CS-18/24 decisions, PR #6's schema/domain guard, and Aryan's implementation instructions.

| Decision | Implementation | Acceptance/review status |
|---|---|---|
| Mandatory matrix C02 | Name, purpose, date/start/end/zone, positive attendance and venue type; Other layout requires venue details. Description, minimum capacity, layout choice, accessibility, equipment and notes are otherwise optional. Registration on requires an ordered opening/closing window. | **Provisional team proposal.** PO/team must confirm venue/layout wording and matrix. No arbitrary future-date/lead-time or capacity relationship rule added. |
| Incomplete drafts | Zero meaningful fields rejected; any one meaningful field (including purpose without a title) saves. Supplied values still receive type/bounds validation. No expiry/autosave. | Explicit user boundary; overrides old “minimum title” audit wording. |
| Timestamp wire adapter | ISO instants with offsets supported. Alan's local date/time fields plus IANA zone also supported as a deliberate BFF/service extension. Store UTC instants and local intent; endDate supports overnight events. Reject DST gaps/repeated clocks rather than silently choosing. | Engineering choice; document in OpenAPI. |
| Idempotency | Required key for every request write; scope actor/method/path/key; compare canonical body hash. Replay original status/body after fresh actor/relationship checks, before version check. Conflicting payload409; retain rows, no 24h purge. | Deliberate strengthening of older draft API; current instructions require durable create/save/resubmit safety. BFF retains an intent key across an uncertain retry while the form remains open. |
| Assignment fairness | Keep Javier's shared load definition/selector. Active workload first; then least recently assigned across all assignment history; never-assigned first; then creation time and ID. Selection and history insertion under one transaction advisory lock. | Aryan selected the fairer policy during implementation. Javier must review the extension; no second engine or user tracking column. |
| Activity granularity | Log actual create/edit/submit/assignment/decision/resubmit actions independently; replay/failure adds none. | CS-44's example total of three conflicts with required separate assignment and edits. **Exact count acceptance remains pending**; legitimate records are retained. |
| Limits | Name100, text4000, options100 ×200 chars; decision notes500 inherited guard; history page20. | Safety bounds/page size are engineering placeholders, not customer-approved limits. |
| Access T02 | Verified roles array authoritative, legacy single-role fallback; owner-private Requests/Drafts; current assigned Coordinator for non-Drafts; same non-null organisation Organisers for actual Event history only. Staff see minimal Event booking options, never request/history values. | Existing CS-24/source policy plus explicit privacy instructions. Authentication retains Marcus's permission service; this branch does not complete broader CS-26 role/permission administration. |
| Request versus Event | Approval creates exactly one distinct Planning Event. Draft/submission do not create an Event or reserve venue/equipment. | Shared schema/guard reused. Confirmation, cancellation, completion and reassignment endpoints are later work. |
| Notifications | Write RequestSubmitted/CoordinatorAssigned/RequestReturned/RequestResubmitted/etc to the existing outbox in the transaction. | Actual delivery/relay is CS-50 and not implemented or claimed. |

The only supporting decision adapter implements assigned approve/reject/return through the shared guard. It enables a real return→amend→resubmit demonstration. Venue/booking business policy is untouched. The old booking contract's Venue Staff creation test remains a separate team defect.
