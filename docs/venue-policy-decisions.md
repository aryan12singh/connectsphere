## Agreement boundary — 14 October 2026

Aryan accepted proposed policies 3–6 in the project discussion. The subsequent PO reply resolves question 1: lock buffers after the first confirmed venue booking and require the Staff → current Coordinator → Organiser communication chain for initial configuration of existing bookings. Q2 was resolved on 17 October: the PO/team reply relayed by Aryan describes a tentative Coordinator request followed by Venue Staff approval on “S3-13a Review booking request — approve / reject with reason”; Aryan explicitly confirmed that no extra Coordinator Confirm button is required. The existing two-action workflow matches. The Booking summary therefore reports no pending venue-policy clarification. Record implementation, acceptance and deployment separately.

The PO's direction does not introduce automatic cancellation, approval resets or a per-booking buffer override. The implementation records Staff's attestation of the communication chain for each affected Event, including current identities, read booking versions, a note and server-recorded time. It cannot prove that an external conversation occurred. Current commitments are collected and checked under Booking's venue lock so a concurrent request, approval or booking change cannot silently bypass the consultation record; current Event assignment/Organiser identity is reread before saving. The legacy opportunity is consumed once per venue. Booking determines whether it has ever had a confirmed booking, including moved/cancelled confirmation history, and records `configuredAfterConfirmation` in the immutable configuration receipt. True retains the confirmation lock; false clears the blanket legacy lock and preserves ordinary pre-confirmation edits. A caller cannot choose the lock outcome. Unrelated catalogue maintenance remains permitted.

The legacy migration grants that opportunity only to locked venues that existed when the original blanket-freeze migration completed, preserving existing values and history. A venue with a provisional confirmation fence follows a separate safe recovery path: an ordinary Staff buffer edit may clear the fence only under Booking's venue lock after proving there has never been a confirmed booking at that venue, including moved/cancelled confirmation history. A recorded `VENUE_BUFFERS_LOCKED` provisional fence must exist; the legacy allowance must not be pending; every retained legacy configuration receipt, if any, must explicitly say `configuredAfterConfirmation:false`. True or missing receipt classification denies recovery. The server records the recovery and recheck atomically. Missing/stale/dependency proof fails closed; a failed confirmation attempt never authorizes blanket automatic unlocking. The form uses matching-version server permission to expose this recovery.

Two internal prospective test decisions are now settled under Aryan's authorization: physical/hybrid capacity is a hard search requirement, so under-capacity venues are excluded even from partial results; an omitted hold deadline uses the agreed 72-hour default capped at setup start, while explicitly invalid or past deadlines are rejected. These internal test decisions were separate from Q2, subsequently resolved by the 17 October clarification above. The current blue cases in CS-36/37 are reconciled and their original source expectations retained as superseded proposals; historical execution results are unchanged.

Room headcounts represent disjoint planned allocations during simultaneous venue use. Required rooms must account for the Event expected attendance at every booked session segment. Unbooked schedule gaps may represent breaks or travel and are not inferred to require a room. Staff must validate the configured physical capacity for the selected supported layout; the existing single Venue capacity must be safe for every supported layout (there is no independent per-layout capacity matrix). The primary location never supplies a registration limit. Registration must not exceed the reviewed attendance plan; the shared Event/registration owners implement that command boundary.

Pending extension requests do not change expiry. Arrangement edits clear the request for a fresh review; a consumed extension remains consumed. A reassigned Coordinator must submit their own request. The migration backfills consumed extensions from retained VenueHoldExtended outbox history; it never shortens historical deadlines. Expiry remains effective immediately on reads; the existing production scheduler records deadline audit and notification intents under CS-90. Message consumers must resolve current assignment and suppress stale deadline notices after an extension, cancellation or approval.

## Arrangement review and restoration — 23 October 2026

Changing or cancelling a Staff-approved booking requires an explicit current-Coordinator review bound to that booking version and exact proposal. Last effective venue cancellation additionally requires `confirmLastVenue`; the Event and registrations remain. Operational saves require a fresh overlap preview and explicit confirmation when current holds/bookings are affected. The five categories are Maintenance, Equipment failure, Renovation, Safety concern and Other. Organisers receive venue, period, category and next action; the internal note remains private.

A pending replacement is not an effective final venue. The current Coordinator explicitly withdraws it before Staff can restore the original. Restoration rechecks full occupied-window availability and suitability; shortening/removing a block alone never restores. A replaced original is historical. Effective replacements require current Safety and separate Event reconfirmation before attendee details/notices change. Unaffected commitments and all registrations survive. Whole-Event cancellation remains the separate CS-54 workflow.
